# 02 · 候选方向短名单

评估维度：**痛点真实性 · 竞品密度 · 开源适配度（为什么必须开源） · 个人可交付性 · 长期复利**

---

## 方向 A：插件合规与兼容性公共设施（推荐）

**一句话**：把"官方最佳实践"变成可执行的检查规则，并发布**经过实际验证**的"插件 × DSH 版本"兼容矩阵。

- **痛点证据**
  - DSH 迭代快（本机 0.2.0-rc.2，alpha 已到 0.2.1-alpha.2），插件极易随宿主升级而失效；生态里"升级安全"已经是一个**被验证有需求**的品类（my-guardian 31K、plugin-console 19.6K、update-checker 8.3K），但这些都是**事后补救**。
  - 官方 practices 文档写死了大量硬规则（例如：waterfall 监听器不 return next() 会截断他人、写未知 session event type 会导致会话无法重开、用 session/event 全量重扫会拖垮性能、客户端 import 官方 Client 包会随版本崩），**目前没有任何工具能检查这些**（检索命中 8 条，均不相关）。
  - "我的插件在哪个 DSH 版本上能用"没有任何公开答案（检索命中 3 条，均不相关）。
- **竞品**：dsh-plugin-doctor（只看包结构）、dsh-testkit（只看你能不能装/卸）、dsh-trust-check（只看能力与安全）。**没有人看"代码写得对不对、能不能跨版本活下来"。**
- **为什么必须开源**：规则来自社区踩坑，必须可审计、可提 PR；兼容矩阵必须是中立第三方结论，任何厂商自证都不可信。
- **首个里程碑**：`npx dsh-plugin-lint` 对插件目录跑 12 条规则 → 终端 + JSON 报告；接一个 GitHub Action；对 20 个热门插件跑一遍，公开"踩雷榜"。**这个榜单本身就是最好的传播素材。**
- **风险**：静态分析有误报；规则要跟着 DSH 演进维护；受众是插件作者（人数少但影响力大）。
- **复利**：规则集 → 成为事实标准 → 官方可能收编；矩阵数据 → 生态基础设施。

## 方向 B：插件构成冲突检查器（可作为 A 的第二模块）

**一句话**：装了一堆插件后，谁抢了谁的 slot / 工具名 / HTTP 路由 / 配置行 / 提示词位置？给出冲突报告和处置建议。

- **痛点证据**：聚合包盛行（dsh-web-all 一个包塞 18 个插件、dsh-suite 18 个），用户 profile 里动辄 20+ 插件；官方 plugin_manager 明确警告"启用顺序会改变配置优先级"。
- **竞品**：无专做此事的插件（目录检索无命中）。
- **可交付性高**：官方 `@deepseek-ai/dsh-host-plugin-inventory` 已经提供"Cordis Loader 插件状态的只读投影"，可以直接读真实运行态，不用猜。
- **风险**：需要判定的"冲突"边界较多，第一版建议只做**确定性冲突**（同名工具、同路由、同 row id、同 slot key）。

## 方向 C：DSH Web 无障碍（a11y）层

**一句话**：键盘全流程可用、焦点可见、读屏可读、支持减少动效与高对比。

- **痛点证据**：检索 28 条"无障碍"命中**全部**是 computer-use 相关（macOS AX API），**没有一条在改 Harness 自己的 UI**。这是本次调研中唯一"完全无人"的 C 端方向。
- **为什么适合开源**：无障碍天然是社区驱动、需要真实用户反馈的公益属性工作，也容易获得官方接受（官方仓库 MIT 且活跃）。
- **风险（重要）**：官方 practices 明确要求插件**不要操作宿主 DOM、不要读别的插件的 DOM**，所以"用插件修宿主 UI"存在模型冲突。更现实的路径是：**审计 + 报告 + 向上游提 PR**，插件只承载"可配置的增强"（如快捷键、命令面板、对比度主题）。
- **建议**：如果选这个方向，第一步不是写插件，而是**产出一份 DSH Web 无障碍审计报告**，用报告换官方协作。

## 方向 D：UI 多语言（社区本地化中心）

**一句话**：一个众包翻译中心，让 DSH 界面和插件 UI 支持任意语言。

- **痛点证据**：官方只有 zh/en；社区只有一个俄语包（14.8K/月，说明有需求）；4,508 个插件绝大多数只有中/英单语。
- **为什么适合开源**：众包翻译必须开源；翻译质量靠社区。
- **风险**：需要验证"插件能否为**别人的命名空间**注入语言包"（技术上要与 `ctx.locale` 的能力对齐，存在做不了的可能）；众包项目需要冷启动。

## 方向 E：薄分类里的单点产品

从覆盖最薄的分类里选一个做垂直产品：`agi`(17) / `identity`(24) / `voice`(65) / `docs`(68) / `wsl`(77)。

- 优点：竞争少，叙事清楚，容易做出"第一个"。
- 缺点：分类薄往往说明**需求也薄**，或者已被某个头部产品跨界覆盖（例：identity 被 dsh-im 62K 覆盖）。需要先做需求验证。

| 记忆 / 上下文压缩 | 200+ 实现，头部 140K/月 |
| 用量计费 | 头部 107K/月，且有多个 |

| 远程 / 手机访问 | 多个 100K+ 级实现 |
| 网页搜索 provider | 24 引擎的免费搜索已有 |
| 另做一个脚手架 | create-dsh-plugin(-cli) 已存在，天花板低 |
